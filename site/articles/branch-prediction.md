---
title: "Branch Prediction: Guessing the Future 20 Times a Second, Billions of Times a Second"
category: Low-Level Architecture
summary: Modern CPUs guess which way an if-statement will go before they know the answer, and are right often enough that guessing wrong is the expensive part.
---

Somewhere in a running program there's a line like `if (x > 0) { doA(); } else { doB(); }`. To a programmer this is a simple decision. To the CPU executing it, it's a moment of genuine uncertainty that has to be resolved before the chip knows what instructions to fetch next — and modern processors resolve it by guessing, correctly, roughly 90-95% of the time, using hardware built specifically to guess well.

To see why this matters, you have to know how a CPU actually processes instructions: not one at a time, start to finish, but in an overlapping pipeline, where fetching instruction 5 starts while instruction 4 is still decoding and instruction 3 is still executing. This overlap is where most of a modern chip's speed comes from. But a conditional branch is a hole in the pipeline: the CPU can't know whether the *next* instruction to fetch is doA() or doB() until the comparison `x > 0` actually finishes executing, several pipeline stages later. If the CPU just waited for the answer every time, it would stall the entire pipeline on every single if-statement — and a typical program has a branch every five to ten instructions.

Waiting isn't acceptable, so the CPU doesn't wait. It guesses which way the branch will go, based on the branch's past behavior, and keeps fetching and executing instructions down the guessed path speculatively — meaning provisionally, without committing the results yet. A dedicated piece of hardware called the **branch predictor** makes this guess, and it's shockingly good, because most branches in real programs aren't random. A loop condition that runs 999 times and exits once is "taken" 999 times in a row; a null-check that almost never triggers is "not taken" nearly every time. The predictor keeps a small history — essentially, a table remembering how this branch (and similar recent branches) resolved recently — and bets on the pattern continuing, which it usually does. Modern predictors on desktop-class chips are correct well over 90% of the time, some approaching 97-98% on well-behaved code.

The two outcomes after a guess are not symmetric. A correct guess costs essentially nothing extra — the pipeline just continues as if it always knew the answer, which is the entire point. A wrong guess is expensive: every instruction fetched, decoded, and speculatively executed down the wrong path has to be thrown away, and the pipeline has to restart from the correct path, which on a deep modern pipeline can cost 15-20 cycles or more. This is why branch mispredictions show up so directly in profiling data as unexplained slowness in code that "should" be fast — the arithmetic is trivial, but the pipeline keeps guessing wrong about which arithmetic to do next.

This also explains a piece of advice that seems bizarre out of context: sorting an array before running comparisons on it can make a loop measurably faster, even though sorting is extra work and doesn't change how many comparisons happen. An unsorted array makes each `if (x[i] > threshold)` essentially a coin flip from the predictor's point of view — no pattern to learn, roughly 50% misprediction rate, maximum pipeline flushing. A sorted array turns the same loop into one long run of "taken," then one long run of "not taken" — a pattern the predictor locks onto almost immediately, dropping the misprediction rate close to zero. The comparisons are identical; the only thing that changed is how predictable their order is, and predictability is what the hardware is actually pricing.

Speculative execution research since 2018 has also made branch prediction famous for a less flattering reason: Spectre and related attacks exploit exactly this speculative window, tricking a CPU into speculatively executing code down a mispredicted path that touches memory it shouldn't, and using timing side effects left behind before the rollback to leak data. The performance trick and the security vulnerability are the same mechanism, viewed from two different angles — which is a fair summary of a lot of computer architecture.
